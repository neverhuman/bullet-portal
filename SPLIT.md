Status: first-build operations portal; projection only, not release-ready
Owner: Bullet Farm maintainers
Last reviewed: 2026-08-25
Applies to: bullet-portal

## Role

Vite + React operations portal. Fifteen hash-routed spec §25 surfaces
(`src/surfaces.ts`): nine read farmd through the projection contract in
`docs/projections.md` — one atomic ledger snapshot
`{data, as_of_sequence, observed_at, source}` per route, cross-checked against
the `x-bullet-as-of-sequence` header, one shared watermark per composed view —
and six render explicit UNKNOWN naming their missing ledger subject. Pending
versus verified mutations through the session-bound `POST /v1/commands` path;
only durable `VERIFIED` is green. The exact built-`dist` bundle-manifest
subject (`ops/build/`, `.bullet-portal-bundle-v1.json`, framed BLAKE3 root)
is the artifact a package may embed. UNKNOWN stays unknown; the browser holds
no authority.

## Split Rules

- Jeryu is the initial source forge; GitHub is a configurable effect adapter,
  not source authority.
- The kernel is the only authority. The portal projects `bullet-kernel`'s
  public API and never invents a DTO, a status, or an empty list.
- `src/generated/` is a generated zone (`agent/generated-zones.toml`):
  `api.ts` is copied verbatim from `bullet-kernel/contracts/generated/api.ts`
  and `schemaBundle.ts` from the hub through `scripts/sync-family-contracts.sh`.
  Never hand-edit; regenerate from the source contract.
- Committed files must not depend on sibling checkout paths. Only
  `ops/ci/real-farmd.sh` resolves the sibling `../bullet-kernel` at run time,
  and it fails closed when that checkout is absent.
- Browser requests stay same-origin through the Vite proxy; `VITE_BULLET_API`
  stays unset in development and proof lanes.
- Release builds depend on immutable tags, not branches. The bundle manifest is
  regenerated by `npm run bundle:generate` and drift fails `npm run bundle:check`.
- Zero new worktrees; edit only the claimed canonical checkout.
